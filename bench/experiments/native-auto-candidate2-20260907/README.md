## Managed challenge routing

The first two candidate-1 rounds include six automatic timeouts in pairs where native returned
useful content; only one timeout reached native. Static inspection found that the traditional
ladder uses the existing managed-challenge discriminator, while the automatic branch did not.
The saved public excerpts do not preserve the raw HTML needed to attribute each loss to that
marker, so this remains a testable routing hypothesis rather than an established public gain.

Automatic now passes that existing discriminator to the transition planner. A positively
classified managed challenge can skip to permitted headful emulation, while an ordinary
interstitial retains cheaper exploration. Native remains last, lower ceilings are respected,
and a failed promoted headful route does not backtrack to weaker routes. This evidence is used
within the call only; it is not stored as a fingerprint-wall sample. No deadline, wait, admission
budget or attempt ceiling changes.

The regression failed with route index 1 instead of 3 before the behavior change. All 12 core
tests pass afterward; see `managed-routing-red.txt` and `managed-routing-green.txt`. A local
browser fixture with a two-attempt ceiling checks that the response's marker reaches the planner
and yields the expected content through HTTP/real without native. It passed in the manual group
at the start of current-tree QC; the eight automatic tests took 27.88 seconds in total, the
learning test 6.48 seconds and the native-timeout test 12.44 seconds. The four local browser tests
passed in 54.83 seconds. These counts do not imply every ignored network test has been executed.

## Short-page warm-wait hypothesis: not retained

Candidate 1's native example-page calls spent about 21 seconds in the warm loop, ended at its
deadline and then delivered a short page. Reusing the final short-page acceptance rule inside
that loop appears faster, but nonempty `Empty` content can also be an unfinished application.

The frozen pre-change CLI was checked against three local fixtures; see
`warm-wait-probe.py` and `warm-wait-probe.json`. The static short page spent 6.3 seconds in the
diagnostic six-second warm budget. A delayed application returned only `Loading...` through
native real mode, while native warm waited and returned the completed report. Both initial
documents have short nonempty text and more than 6,000 HTML bytes, the same classification
condition involved in the proposed shortcut. This is evidence against blanket early acceptance,
not proof that every short page needs the default wait.

No warm-wait product change is retained from this probe. A safe optimization needs additional
readiness evidence; text length alone cannot distinguish these cases. The public comparison's
20-second base warm wait, caller deadline and other budgets remain unchanged. These three
loopback calls used separate local homes and did not touch public accounting. The corpus process
was active, so their elapsed times are diagnostic observations rather than benchmark gains.
